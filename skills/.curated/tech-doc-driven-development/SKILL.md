# 技术文档驱动开发

## 核心模型

先确定路线，再生成实现步骤，最后逐步实施和回填。让人负责方向与确认，让 AI 负责调查、表达、实现和记录。

- 把技术路线文档写给人看，把技术实现文档写给执行者和 AI 看。
- 把技术实现文档维护为同一份渐进文档：先生成“计划态”，每完成一步再把该步补成“完全态”。
- 以仓库、代码、配置、测试和用户确认作为事实来源，不凭空补全路径、符号或完成结果。
- 保持技术路线稳定。通常只纠正技术实现；路线确实错误时，先修路线，再同步实现文档，最后改代码。
- 每次只执行一个步骤。完成回填后停止，交给开发者 review；不要在一次对话中跨步骤修改代码。
- 控制每次 diff。发现额外工作时先调整当前步骤或登记后续步骤，不顺手扩张范围。

## 选择工作阶段

根据用户请求只进入必要阶段：

1. **只写路线**：完成技术路线文档并等待确认。
2. **写路线和实现计划**：确认路线，调查工程，生成计划态技术实现文档；每一步写到“加什么功能”为止。
3. **按计划开发**：从第一个未完成且依赖满足的步骤开始，只执行该步骤，并把它由计划态补成完全态。
4. **纠偏**：定位最早偏移步骤，先修步骤计划，再修代码和完成记录。

优先沿用现有文档和章节顺序。不要因格式不同而重写已确认、已落地的事实。

## 阶段一：收集事实与人的路线意图

先获得需求背景、目标、非目标、约束、验收标准和开发者的总体思路。缺少会改变路线的信息时，提出少量、具体的问题；不要替人决定关键业务路线。

- 把 PRD 明示事实、工程事实、开发者决策和待确认项分开；不得把合理猜测写成已冻结规则。
- 遇到“可选、兼容、原样、失败场景”等存在多种解释的业务语义时，先询问其边界；当前阶段不能获得答案时，在文档中标为待确认并阻止相关步骤实施。
- 不因追求完整而扩展 PRD 未要求的输入形态、失败链路、兼容行为或验收项。

需要生成技术实现文档时，先调查真实工程：

- 阅读仓库约束、现有设计文档和相邻实现。
- 追踪入口、核心调用链、数据结构、配置、存储、测试、发布和回滚影响。
- 记录准确的文件路径、关键符号和既有能力；无法确认的内容标为待调查或待确认。
- 检查工作树状态，保护用户已有改动，不把无关变更纳入步骤。
- 区分当前静态事实和未验证的线上、实验、发布或协作状态。

## 阶段二：生成技术路线文档

读取 [技术路线模板](references/technical-route-template.md)，采用完全体路线文档的紧凑结构：

1. `背景`：用一段话说明为什么做、当前问题和本需求新增差异。
2. `目标`：用一段话写最终要达到的、尽可能量化的业务结果；不写技术实现。
3. `整体链路`：默认用一张 Mermaid 流程图串起从输入到输出的关键节点。
4. `方案`：把 PRD 业务语言结合现有代码链路翻译成可落地技术语言；说人话，但必须精确。
5. `验收标准`：逐项写明代码落地后应出现的实际表现，包括正常、失败或降级结果。
6. `范围`：简明界定本次逻辑链路包含和不包含什么。

路线文档固定使用以上六个主章节。联调、发布、迁移、协议和模块职责等内容只有适用时才作为 `方案` 的子节，不新增同级结构。

写作时：

- 用普通人能理解的语言，避免堆砌类名、函数名和实现细节。
- 每个要点尽量不超过 100 个汉字，一个要点只表达一个结论。
- `整体链路` 优先只保留一张流程图；只有流程图无法准确表达时，才补架构图或时序图。
- 用图或两列表格表达复杂关系，表格单元保持短而准确。
- 方案必须逐项覆盖 PRD 要求，并由真实工程链路支撑；不要在路线文档中下钻到文件、类或函数。
- 方案和验收不得自行补充 PRD 未定义的业务语义；待确认项要显式保留，不能伪装成确定结论。
- 让完全不了解项目的人在 10 分钟内理解，并能复述背景、目标、路线、验收和边界。
- 不默认增加“文档状态、Owner、路线决策表、路线确认”等管理字段；只有用户或既有文档要求时才添加。
- 在对话中取得路线确认。路线存在关键分歧时，给出选项、影响和建议，不直接进入实现。

## 阶段三：生成计划态技术实现文档

只在理解技术路线且调查过工程后，读取 [技术实现模板](references/technical-implementation-template.md)。

先用一句话说明实施顺序，再用整体流程图展示步骤依赖。随后按依赖顺序列出所有编号步骤。

每个步骤的计划态只允许包含四项：

```markdown
## N. <步骤名>

去哪：<要修改或协同确认的文件、模块或入口>。

干什么：<结合当前上下文说明本步具体怎么改>。

加什么功能：<说明本步完成后的能力和路线映射>。
```

遵守以下硬约束：

- 初次生成实现文档时，写完“加什么功能”后立即进入下一步骤或结束文档。
- 不得预写 `✅`、完成结论、实际修改、详细设计、范围边界、验证结果、变更文件、Code Review 或 MR 信息。
- 不得为未实施步骤创建“待实现”的落地占位块；没有内容比虚构结果更清楚。
- `去哪` 写准确的文件、模块或协作入口；不确认的路径不要写成事实。
- `干什么` 写实现动作和关键约束，不提前声称代码已存在或验证已通过。
- `加什么功能` 写可观察能力；验收型步骤可以明确“本步骤不新增生产功能”。
- 让每一步形成可独立实现、验证和 review 的小 diff。若涉及多条可独立链路，继续拆分。
- 把协议冻结、基础能力、链路接入、不同形态、响应投影、测试验收按真实依赖排序，不为凑格式强行套阶段。

## 阶段四：单步实现并补成完全态

执行一个步骤时：

1. 重新核对该步骤与技术路线、当前代码和用户已有改动。
2. 只改该步骤“去哪 / 干什么 / 加什么功能”覆盖的范围；范围必须变化时，先修正文档中的这三项并说明原因。
3. 运行与风险相称的验证，区分通过、失败和因环境限制而跳过。
4. 检查本步 diff，排除无关修改。
5. 在该步骤的“加什么功能”之后就地追加真实完成内容，不创建独立的“落地实现项”模板块。

实现代码时坚持“简洁克制”：

- 优先复用现有链路、数据和抽象；能改已有实现就不新增重复文件、层级或旁路。
- 只实现当前步骤和真实需求需要的正常、失败与边界行为；不为几乎不可能发生的情况堆叠防御分支、字段或配置。
- 不用临时变量或派生状态重复存储已有信息；让单一事实来源保持清晰。
- 本轮尚未发布的功能发生调整时，直接收敛当前设计并删除废弃分支；除非需要兼容已发布行为或真实迁移过程，不叠加 legacy 兼容逻辑。
- Review 只报告代码和验证能够证明的问题，不为迎合提问强行制造问题，也不默认用户假设成立。
- 如果新增复杂度确有必要，在当前步骤中写清约束、替代方案和采用理由。

追加内容从以下两项开始：

```markdown
✅

**完成结论：** <用一段话概括实际完成的能力、关键边界和结论>。
```

随后根据本步实际内容使用四级标题组织细节，例如：

- `#### 实际修改`、`#### 数据流与处理方式`、`#### 协议或配置变更`；
- `#### 兼容与范围边界` 或 `#### 最小改动边界`；
- `#### 验证` 或 `#### 校验`；
- `#### 变更文件`；
- 本步骤特有的字段矩阵、降级矩阵、Golden 数据或 Sources。

回填必须说清：

- 实际修改了哪些类、函数、字段、配置、图接线和文档；
- 为什么这些改动与路线和本步计划一致；
- 哪些逻辑复用、哪些新增、哪些删除、哪些明确没有修改，以及是否引入了必要复杂度；
- 验证命令、真实结果、失败和跳过原因；
- 变更文件及需要开发者重点 review 的位置；
- 偏移、纠偏、剩余风险和后续动作；没有就明确写“没有”。

保持所有未执行步骤仍处于计划态，只保留四项。不得把计划中的修改写成已完成，也不得把跳过的验证写成通过。

完成回填后停止继续实现，向开发者交付本步 diff、验证结果和 review 要点，等待确认再进入下一步。

## 阶段五：Review、MR 与发布记录

只在事件真实发生后追加文档末尾的全局记录：

- 完成一次整体 Code Review 后，追加 `## Code Review 记录`，写时间、结论、发现、修复和复验结果。
- 创建或审批 MR 后，追加 `## MR 审批信息`，写真实链接、分支、审批结论和合并后事项。
- 发布、白名单、实验或真机验证尚未执行时，明确写“待执行”，不要标成完成。

不要在计划态文档中预建这些章节。

## 阶段六：纠偏

每一步后比较“技术路线 → 去哪 / 干什么 / 加什么功能 → 实际 diff → 完成记录”，定位最早不一致处。

- 实现偏移：先修正当前步骤的三项计划，再改代码，最后重写该步骤的完成记录。
- 路线错误：先更新并重新确认技术路线，再同步所有受影响步骤，之后才改代码。
- 复杂度偏移：定位重复链路、无效防御、派生状态或未发布兼容包袱，先把基础实现项收敛到最小设计，再小步删除或替换。
- 采用小步增删，不一次推翻整体架构；明确哪些后续步骤需要重排。
- 从最早偏移步骤开始修，避免在错误方向上继续堆叠变更。

## 完成条件

仅在以下条件全部满足时声明交付完成：

- 技术路线已确认，最终实现仍与背景、目标、整体链路、验收和范围对齐。
- 每个编号步骤都已追加 `✅`、真实完成结论和必要的实现细节。
- 验收项已验证；失败、跳过和未执行项有明确结论。
- 技术实现文档中的文件、符号、配置、数据流和最终代码一致。
- 整体 Review 已完成；MR、发布和联调记录只反映真实状态。
- 没有未记录的跨范围改动；剩余风险和后续事项已显式列出。

若用户未指定文档位置，优先遵循仓库既有约定；没有约定时，在说明默认路径后使用 `docs/<需求名>/technical-route.md` 和 `docs/<需求名>/technical-implementation.md`。只要求聊天内草稿时，不创建文件。
